# Правила кода

## Формат

- UTF-8, окончания строк LF, новая строка в конце файла.
- JS/TS/TSX, JSON, CSS и YAML: два пробела на уровень вложенности, без смешивания табов и пробелов.
- JS/TS: точки с запятой, одинарные кавычки, завершающие запятые в многострочных структурах.
- Предпочтительная ширина — 100 символов; окончательное форматирование выполняет Prettier.
- Табуляция допустима в Makefile, если он появится и требует её по синтаксису.
- Пустые строки разделяют логические части; нет случайных отступов и пробелов в конце строк.

Настройки уже находятся в `.editorconfig` и `.prettierrc.json`. В E1 устанавливаются сами инструменты и проверки CI, а для VS Code добавляется форматирование при сохранении.

## Имена

| Объект | Правило |
| --- | --- |
| Функции и переменные | `camelCase`; функция называет действие |
| Компоненты и типы | `PascalCase` |
| Константы конфигурации | `SCREAMING_SNAKE_CASE`, когда это именно константа |
| Файлы компонентов | `StudyCard.tsx` |
| Остальные TS-файлы | `study-session.service.ts`, `answer.schema.ts` |
| Таблицы и столбцы SQL | `snake_case` |
| Коммиты | `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:` |

Имена кода и контрактов — на английском. Тексты интерфейса находятся в ресурсах локализации. Комментарии объясняют причину решения; не пересказывают очевидную строку кода.

## Типы и границы

- `strict: true`; явные типы входа/выхода публичных функций.
- На внешней границе данные считаются `unknown` и проверяются схемой; `any` не используется для обхода ошибок типов.
- DTO определяются отдельно от ORM-моделей. Общие контракты не импортируют серверные библиотеки.
- Компоненты не выполняют SQL и не содержат алгоритм планирования повторений.
- HTTP-контроллеры принимают/выдают данные и вызывают сценарии. Транзакции и права доступа принадлежат сценариям.
- Случайность и текущее время передаются в учебный движок явно.
- Экспортируется только публичный интерфейс модуля; циклические зависимости устраняются.

## Ошибки и асинхронность

Ошибки не проглатываются пустым `catch`. Пользователь получает понятный результат, журнал — контекст и request ID. Незавершённые обещания, загрузки и подписки имеют ясный жизненный цикл. Запрос может быть повторён, поэтому операции ответов и фоновых задач используют ключ идемпотентности.

## Проверка изменений

Прикладная задача сопровождается проверкой типов, форматирования, сборки и необходимыми тестами поведения. Тесты должны проверять полезный сценарий или риск: права на чужой набор, повторную доставку ответа, расписание повторений, конфликт ревизий, восстановление сессии. Не создаются тесты, которые лишь повторяют каждую строку реализации.

Документационную инициализацию проверяем чтением файлов, синтаксисом JSON/YAML, корректностью ссылок и diff. Она не требует запуска ещё не существующих web/api и не считается протестированным приложением.
